# Changelog – ESP CAN bridge Weishaupt (WeAct CAN485, ESPHome)


## v42 (in progress)
- **Write protection for the WEM – write as rarely as possible.** Reason: for the system units of its heat pumps Weishaupt states 100,000 write accesses to the EEPROM over the lifetime (Modbus TCP data point list, print no. 83807301); for the WEM of a gas boiler no number is known, it belongs to the same device family. Three things: **pre-read** – before switching heating circuit or DHW the firmware reads the value on the WEM and does not write if it is already set (`befehl/status`: `vorgemerkt` → `bestaetigt` with `wem` = `nicht_gesendet`; phone app: „stand schon so – nichts geschrieben“ ("was already set – nothing written")). **Write counter** – „Schreibvorgaenge letzte Stunde“ ("writes in the last hour") and „Schreibvorgaenge gesamt“ ("writes in total"; stored, counts from this update). **Hourly limit** – „Schreibvorgaenge je Stunde hoechstens“ ("writes per hour at most"; default 30, 1–120, experts); once it is reached the board does not send (`gescheitert`, `grund` = `obergrenze`). Counted and limited: switching via CAN and via JSON, free CAN writing, the write field and the DHW push of the Olimex variant; write requests forwarded by the CAN tunnel are not. Shown by [gojux/weishaupt_unofficial](https://github.com/gojux/weishaupt_unofficial) and [aghulas/ha-weishaupt](https://github.com/aghulas/ha-weishaupt) – thank you. ([PROTOKOLL, Write protection](PROTOKOLL.en.md#write-protection-write-as-little-as-possible-from-v42))
- Docs: **Other ways to the installation and related projects** ([PROTOKOLL, section 10d](PROTOKOLL.en.md#10d-other-ways-to-the-installation-and-related-projects)) – CAN bus, local JSON interface, WEM portal (app interface and web page), Modbus TCP and WebIF of the heat pumps, older WCM units, each with limits and projects. The measured WEM has neither Modbus TCP nor a web server. The safety rules in the README have a new rule 3 “Write as rarely as possible”.
- **Free CAN writing: further nodes can be enabled.** New text field „Freies CAN-Schreiben: erlaubte Knoten (hex, ab Werk 01)“ ("free CAN writing: permitted nodes (hex, default 01)") in the expert interface. By default it stays with the WEM (`01`); anyone working on the bench with a room unit enters e.g. `01 04`. The boiler (`02`) and `00` can never be enabled, with an invalid list nothing is sent, the object range 2000–5FFF applies to every node, and the switch „Freies CAN-Schreiben“ ("free CAN writing") remains the second hurdle ([PROTOKOLL](PROTOKOLL.en.md#writing-via-can-from-v35-default-since-v42)).
- **Free CAN writing waits for a pause:** it only sends once nothing has run on the SDO channel of the target node for 200 ms (waits at most 3 s), and the result comes as soon as the response is there, instead of after a fixed 2 s.
- New parameter `abstand_can_min` (default 5): smallest configurable interval between two commands via CAN. Smaller only for experiments on the bench – leave it at 5 on the installation.
- Branch `can-tunnel`: the tunnel does not pass the response to one of the board's own write commands on to the other end (`E` in the capture); free CAN writing therefore also works while the tunnel is running.
- Docs: **Restarting the RG2 via CAN** (`0x2559`/0, two write commands – this is how the WEM does it after a changed assignment; reproduced on the bench, sequence with times and comparison with the cold start), **assignment as room sensor** (`0x2604`–`0x2606` on the RG2) and the **measured room temperature in the WEM** (`0x298B`/2 = JSON `02 00 258B 02`, confirmed via JSON by PiLLoX on a WTC-GB 25-B) in [VERSUCHE](VERSUCHE.en.md#assignment-as-room-sensor-and-measured-room-temperature-in-the-wem); plus the settings of both boards for the CAN tunnel side by side.
- `werkzeuge/einstellungen_erzeugen.py` now also resolves placeholders in the limits of a number.
- **Fixed: 327.68 bar and 3276.8 °C after switching on the installation** ([Issue #2](https://github.com/jvejmelka/weishaupt-wem-can-esphome/issues/2), reported by cg089 – thank you). The boiler reports “no value” as `0x8000` in 2 bytes. The firmware always read responses from the boiler (`0x582`) as 4 bytes, without looking at the length in the command byte: `0x8000` became 32768, i.e. 327.68 bar or 3276.8 °C. The temperatures of the PDOs `0x201` and `0x241` went out unchecked (−3276.8 °C). Now one place reads for all packages (`reg::sdo_roh`, `reg::pdo_lesen`): length from the command byte, 2-byte values signed, `0x8000` and `0x7FFF` are discarded, the last valid value stays. This applies to the boiler values, the values at the WEM, the flow values picked up by listening on `0x6C2` and the PDO temperatures. A range filter per sensor (pressure 0–3 bar, temperature 0–100 °C) is deliberately not built in; it would hide overpressure or frost at the outdoor sensor. Backed by telegrams from a capture of the WTC-GW 15-B ([PROTOKOLL, section 4](PROTOKOLL.en.md#4-what-is-read-on-demand)), test `register_kein_wert`.
- **Rules no longer calculate with “no value”:** in the rule engine, outdoor temperature and flow setpoint keep the last valid state on `0x8000` instead of seeing −3276.8 °C for a moment.
- Negative 2-byte values of the boiler arrive signed (previously 6553.1 instead of −0.5).
- Docs: where the WEM stores its network settings (JSON module MI 06: address assignment, IP address, netmask, gateway, DNS, MAC address, device name, name in the certificate) – only the addresses, without values, from [JS-DE-Tech/hacs-weishaupt-lan](https://github.com/JS-DE-Tech/hacs-weishaupt-lan) (MIT), unverified ([PROTOKOLL, section 7a](PROTOKOLL.en.md#7a-objects-taken-from-other-projects-unverified)). The firmware does not read or publish these values.
- Docs: the limits of the heating curve slope depend on the heating circuit type (pointed out by ChristophKomenda, [VERSUCHE](VERSUCHE.en.md)); reference to geronet1's object list for extension module and solar (now under MIT).
- **Fixed: the DHW operating mode was read during the start-up pause.** The DHW cycle only checked “bus is alive”, not the start-up pause (1 min after the start of the board, 10 min after a bus failure). If a reason arose during the pause – „Status lesen“ ("read status"), changed status bits –, three read requests went to the WEM 8 s later, although the message says „angefordert – Anlaufpause, liest danach“ ("requested – start-up pause, reads afterwards"). Now it waits like the heating circuit cycle; the reason is not lost and is read once after the pause. Test `kern_ww_lesung_wartet_die_anlaufpause_ab`.
- **Additional displays: one age limit for both apps.** Until now the Docker app showed values as „--“ after 10 min, the app on the board only after 2 h. Now 2 h applies everywhere (battery sensors often only send on change; Docker: `ZUSATZ_MAX_ALTER_MS`), and anything older than 10 min is shown dimmed with its age („20,6 °C (35 min)“); „läuft“ ("running") then does not pulse.
- Display „Eigene CAN-Anfragen“ ("own CAN requests") with the switch off: „aus - keine Abfragen im Takt (Betriebsarten bei Anlass)“ ("off – no scheduled requests (operating modes when there is a reason)") instead of „aus - nur mithoeren …“ ("off – listening only …") – after all, the board keeps switching and reading when there is a reason.
- [Ways to the heating system](PROTOKOLL.en.md#ways-to-the-heating-system): row for the DHW push of the Olimex variant (writes `0x2A49`/2 at the WEM, independent of the switch „Freies CAN-Schreiben“ ("free CAN writing")). Overview drawing: the phone app is built into the board, the Docker app is the second option.
- **Docs reorganised:** PROTOKOLL.md now describes only the bus; at the front is the table [Ways to the heating system](PROTOKOLL.en.md#ways-to-the-heating-system) as the one place for “what talks to the heating system in which way, what is on by default”. Operation, settings, rules and additional displays (previously sections 6, 6a, 6b) are in [FIRMWARE.en.md](FIRMWARE.en.md), room unit WEM-RG2 and CAN tunnel (10a, 10b) in [VERSUCHE.en.md](VERSUCHE.en.md). The old headings remain in PROTOKOLL.md as a reference, so old links still lead to their target. Section 5 is now called “Writing at the WEM: via JSON and via CAN”. The table of all settings and every “by default” statement are generated from the code (`werkzeuge/einstellungen_erzeugen.py`), and the CI checks this.
- **Olimex ESP32-EVB and further values via CAN – contribution by cg089** ([fork](https://github.com/cg089/weishaupt-wem-can-esphome), branch `olimex-esp32-evb`), built into the packages here: `olimex-weishaupt.yaml` (Ethernet LAN8720, CAN on GPIO5/GPIO35, Home Assistant API, without SD/LittleFS), package `kraiz-per-can` (29 objects of the integration kraiz/hassio-weishaupt via CAN instead of JSON, button „Warmwasser-Push“ ("DHW push") `0x2A49/2`, error block `0x273F` of the WEM every 2 min with status, number, module and plain text), package `dallas` (1-Wire bus for DS18B20), tools `werkzeuge/kraiz-per-can/`. Instructions: [OLIMEX-ESP32-EVB.en.md](OLIMEX-ESP32-EVB.en.md). The plain-text error uses this project's own texts from `fehlercodes.yaml`; the manual texts typed out in the fork have not been taken over (rights with Weishaupt). Compiled, not yet run on an Olimex board in this version.
- **Olimex: comparison with the fork.** `werkzeuge/olimex_vergleich.py` compares what ESPHome makes of the fork's Olimex YAML and of the one here: 123 of 124 entities are identical in all fields including lambdas, the one exception is „Letzte Emergency-Meldung“ ("last emergency message"; here „Meldung WEM“/„Meldung Kessel“, "message WEM"/"message boiler"). `tests/olimex-fork-soll.txt` records the fork's entities, and the CI checks against it.
- **Package `netz-wlan`:** Wi-Fi displays and Wi-Fi change have been moved out of `kessel.yaml` into a package of their own, so that boards with Ethernet (`netz-lan`) use `kessel` unchanged. **Anyone maintaining their own main YAML adds the line `netz: !include pakete/netz-wlan.yaml` under `packages:`** – otherwise the Wi-Fi fields are missing and the package `app` does not build. CAN pins configurable via `can_tx_pin`/`can_rx_pin` (default GPIO27/GPIO26 as before).
- **Licence information:** [LIZENZEN-DRITTER.en.md](LIZENZEN-DRITTER.en.md) names ESPHome, ESP-IDF, littlefs, ArduinoJson, kraiz and the parts that are only linked; the releases include `LICENSE` and this file and point out that the finished firmware as a whole is under the GPL-3.0 because of ESPHome.
- **Fault messages in plain text:** EMCY of the WEM (`0x081`) and of the boiler (`0x082`) are picked up by listening and shown as „Meldung WEM“/„Meldung Kessel“ ("message WEM"/"message boiler"), e.g. „W 1501: Verbindung zum Raumgerät RG2 unterbrochen (Teilnehmer 1)“ ("W 1501: connection to room unit RG2 interrupted (participant 1)"). Own short texts DE/EN for all 119 codes of the WTC-GW manual in `fehlercodes.yaml` (generator `werkzeuge/fehlercodes_erzeugen.py`, checked in the CI); original texts not in the repo for copyright reasons, on request from your own PDF with `werkzeuge/fehlertexte_aus_handbuch.py` – then upload them on the settings page („Störmeldungen“ ("fault messages"), expert password, home network only, without a new build) or include them in the build. Language via `meldungen_englisch`. PROTOKOLL section 10c.
- **Fetching values by hand via JSON** (package `json-lesen`, Jürgen's idea): for boards without a CAN cable or during a bus failure. Button „Aktualisieren“ ("refresh"; ↻) in the app as soon as the bus is silent; „Abrufen“ ("fetch") on the settings page; button in the web interface. ONE request with 7 objects (outdoor temperature, heating circuit and DHW operating mode, boiler, burner phase, DHW actual/setpoint), values end up in the same sensors and in the app status as from the bus; the burner start counter stays with the bus. Never automatic; minimum interval 5 min by default (at least 2 min), locked while a JSON switch command is running. Findings at the WEM: at most 7 objects per request (the eighth: CM 05); six fetches in 7 min → empty responses, ok again after 10 min. On the WTC-GW 15-B: values match the bus (outdoor 9.2 °C, boiler 33.9 °C, DHW 37.1 °C).
- **Release image without personal data:** `werkzeuge/release_bauen.py` generates from the main YAML a configuration without Wi-Fi (Improv + open hotspot, no reboot without Wi-Fi), without passwords (first-run setup in the app, random build password for the web interface, which the board replaces anyway), without ESPHome OTA (update only in the browser with the expert password), without MQTT/additional displays, with the MAC suffix in the device name. `werkzeuge/release_paket.py` puts together factory/ota image, `SHA256SUMS` and `manifest.json` (ESP Web Tools) and checks that no placeholder credentials are in the image. CI job „Release-Image“ on every push (artifact), workflow `release.yml` on version tags: GitHub release (pre-release) and installation page `installieren/` on GitHub Pages. CI on ESPHome 2026.9.1.
- **Searching for the WEM on the network** (fallback without CAN cable): settings page and assistant, „Im Netz suchen“ ("search the network"); the assistant starts it on its own when the bus is silent and no address is entered. The board's own /24 network, per address exactly one connection on port 80 and one `GET /`; the WEM is recognised by `WWW-Authenticate: Basic realm="WEM-SG HTTP-Server"`. A task of its own, at most 4 connections at the same time (the ESP32 has 14 sockets for everything – with 16 at the same time the web server was briefly unreachable and the WEM was overlooked). On the WTC-GW 15-B: WEM found in 16 s, web server stayed reachable.
- **Assistant shows the Wi-Fi networks in range:** when opened, the board scans by itself (`esp_wifi_scan_start`, the existing connection stays; ESPHome keeps the results thanks to `request_wifi_scan_results`). List per name with the strongest signal and a padlock for secured networks; tapping takes over the name. On the WTC-GW 15-B: two access points, both the own Wi-Fi – foreign networks do not reach into the boiler room.
- **Setup assistant** (`/einrichtung`): after the passwords have been set, the app leads straight on (the first-run setup passes the admin token along). Step 1 **Netz** ("network"): connected Wi-Fi, address, signal; enter another Wi-Fi (30 s trial, otherwise the previous one stays). Step 2 **Heizung** ("heating system"): CAN bus alive/silent, devices on the bus (heartbeat `0x700+n`: WEM, boiler, EM-HK, EM-Sol), WEM address via CAN (starts on its own when the bus is alive) or by hand, switching path CAN or JSON with recommendation. Step 3 **Fertig** ("done"): summary. Can be opened again via the settings page.
- **Emergency hotspot takes precedence:** if ESPHome's Wi-Fi login page is active (new board without Wi-Fi), the app leaves all GET requests to it – previously the app under `/` covered the login page.
- **WEM address via CAN:** settings page „Heizung (WEM)“ ("heating system (WEM)") → „Per CAN suchen“ ("search via CAN"): three single read requests to the WEM (node 1: `0x2B08` IP, `0x2B09` mask, `0x2B0A` gateway, interval 0.5 s, never at the boiler). Shows whether the reported address matches the entered one, and takes it over at the push of a button (or by hand). On the WTC-GW 15-B: address, mask and gateway read, matches the entered one.
- Version text on the board: „v42-dev vom 11.11.2026“ ("v42-dev of 11 Nov 2026"; ESPHome project version `42-dev` instead of the leftover `27`); README (DE/EN) describes access levels, file system, UI package, SD card, editor for additional displays, partial reset and operation behind a proxy.
- **Admin may no longer access the bus:** the settings of the groups „Lesen“ ("reading"; own CAN requests, long read commands at the boiler, SD files) and „Experten“ ("experts"; free CAN writing, raw capture, watchdog) now change only with the expert password (🔒 on the settings page); a backup without the expert password leaves them unchanged. Admin keeps: switching (CAN/JSON, intervals), rules, appearance, additional displays, app/admin password, info, log, backup, restart. Firmware update, UI package, reset and `/experten` were already expert.
- „Schalten per CAN“ ("switching via CAN") is now the default and the recommendation (`RESTORE_DEFAULT_ON`).
- **Editing additional displays on the settings page:** create, change, remove, save up to 6 entries (name, topic, field, unit, „läuft ab Schwelle“ ("running from threshold")) – same validation and storage as `cmd/zusatz` (script `zs_datei`), takes effect immediately without a restart.
- **Recommendations:** every setting shows its recommended default (◆, switches from their `restore_mode`, numbers like `initial_value`) and marks deviations.
- **Partial reset** (expert password, home network only): settings to the recommendation, clear additional displays, built-in UI, access as delivered (with restart). The full factory reset remains alongside.
- Checked on the WTC-GW 15-B: invalid entry rejected, additional displays cleared and uploaded again (values come with the next MQTT message), wrong password and unknown area rejected.
- **Replacing the UI without a firmware update:** `werkzeuge/app_einbetten.py --paket ui.wui` packs app and settings page into a UI package (header with API version, SHA-256 per file). Upload on the settings page (section „Oberfläche“ ("interface"), expert password): the board checks API version, size and every checksum, puts the package into the file system and serves it from then on; on any error the built-in UI stays. „Zurück auf eingebaute“ ("back to built-in") deletes the package. The info page shows which UI is running, and the API version. `/api/meta` reports `api`.
- The file system needs the directory functions of the ESP-IDF (`require_vfs_dir`), otherwise `rename` fails with ENOSYS.
- Checked on the WTC-GW 15-B: wrong password and modified package (one bit) rejected, valid package active (ETag `p…`), survives a restart, resetting to the built-in one works.
- **File system in the free flash** (option `dateisystem`, on in the board YAML): the component registers the upper 4 MB of an 8 MB flash as partition „dateien“ ("files"; `esp_partition_register_external`) and mounts **LittleFS** there under `/fs` (component `joltwallet/littlefs` 1.23.1). Without a new partition table, so via OTA. Boards with 4 MB report „kein freier Flash“ ("no free flash"). Info page: size and usage. On the WTC-GW 15-B: 4 MB mounted, board runs normally.
- **microSD slot** of the WeAct board (option `sd_karte`, on in the board YAML): the card is mounted at start (FAT, never formatted, 10 MHz SPI on CS 13 / SCK 14 / MOSI 15 / MISO 2); the info page shows name, size and free space or „keine Karte“ ("no card"). WeAct's advice: remove the card when flashing via USB. On the WTC-GW 15-B: no card inserted, board runs normally.
- **Three access levels:** app (switch, view), admin (settings page), **expert** (ESPHome interface `/experten`, `/update`, factory reset). App and admin password are now stored only as a **hash** (PBKDF2-HMAC-SHA256, 16 bytes of salt, 1000 rounds; own implementation, checked against RFC test vectors). The expert password stays readable because ESPHome's digest login needs it; without an expert password the level is locked. All three must be different (when taken over from v41, admin and expert may stay the same until they are changed).
- **Takeover from v41:** the credentials previously stored in plain text are taken over hashed on the first start; the expert level gets the previous password of the web interface.
- **Expert level not from the internet:** requests through the entered reverse proxy to `/experten`, `/update`, `/events`, the value paths and the factory reset are answered by the board itself with 403. Can be enabled temporarily at your own risk (settings page, from the home network only, with the expert password: 1/8/24 h or unlimited, applies until the restart).
- **App token expires after 90 days** (all devices then log in again).
- **Info page shows the flash size:** on the WTC-GW 15-B the WeAct board has **8 MB**, the firmware uses 4 MB – the upper 4 MB are free for files, without changing the partition table (and without a USB cable).
- Checked on the WTC-GW 15-B: takeover of the credentials, app login (0.14 s with hash), admin login, `/experten`, enabling/locking from outside, wrong expert password rejected on factory reset and password change.
- **App with a fixed layout width of 980 px** (`<meta viewport width=980>`): on the phone it now always looks as with Chrome's “Desktop site” – narrow column in the centre, larger font, without having to set anything (operator's request). PC and tablet ignore the setting.
- **`/experten` shows the ESPHome interface completely:** it looked for its data relative to its path (`/experten/events`). At build time the component generates from the installed ESPHome version a copy that looks at the root (`__init__.py`, `experten_index()`), and serves it under `/experten` (+26 KB flash).
- **`/` is the app**, the ESPHome web interface is at **`/experten`** (digest, user `admin`, admin password). For this the app handler registers with the web server before the ESPHome interface. `/events`, entity paths and `/update` stay where they are.
- **Login lock behind a reverse proxy:** `X-Forwarded-For` now only counts if the request comes from the entered proxy address (`app_proxy` in `secrets.yaml`, empty = never). Previously a forged header could have bypassed the lock (pointed out by the operator's proxy).

## v38 – 2026-10-27
- **Phone app directly on the board** (new package `app.yaml`): `http://<board>/app` serves the same app as `app/` – without a server, without Docker. The files from `app/public/` are embedded gzip-compressed (`werkzeuge/app_einbetten.py` → `components/weishaupt_can/app_dateien.h`, about 16 KB together); `/api/login`, `/api/status`, `/api/energie`, `/api/meta`, `/api/mode`, `/api/warmwasser`, `/api/lesen` answer like the Docker app.
  - Login with `app_benutzer`/`app_passwort` from `secrets.yaml`; 5 failed attempts per address in 15 min → 15 min lock (HTTP 429). Session token in flash, survives updates.
  - Switch commands go, like `cmd/heizkreis`/`cmd/warmwasser`, through queue, one-minute lock and verification on the bus; the progress comes from the history of the last 10 commands.
  - Additional displays: the board subscribes to the topics of the list itself (the board's broker account needs read permission for them).
  - The board's web interface under `/` stays unchanged (own password). The service worker of the board app intercepts only its own files.
  - On the WTC-GW 15-B: `/api/status` matches the Docker app (measurements, boiler, switching, bus, additional values); operating mode and status bits are missing after a restart until the board has read or seen them again.
  - **Queue in order of arrival** (previously always heating circuit before DHW): heating → water → heating now sends water before the second heating. A new request for the same target still replaces the old one and joins the end of the queue.
  - **Interval between commands configurable:** „Abstand zwischen Befehlen per CAN (s)“ ("interval between commands via CAN (s)"; default 10 s, 5–300) and „… per JSON (s)“ ("… via JSON (s)"; default 60 s, 60–600). Via CAN the WEM accepts immediately, the interval only spares its EEPROM; the JSON interface still needs at least 1 min. SD files and write commands via JSON count as JSON.
  - Tests: `kern_abstand_einstellbar`, `kern_warteschlange_reihenfolge_des_eingangs`, `app_status_*`, `app_zusatz_zahl`, `app_befehlsverlauf`, `app_login_sperre`, `app_meta_und_energie`, `app_eingebettete_dateien`. CI checks that the embedded app is up to date.

## v37 – 2026-10-26
- **`status/json` → `schalten.weg`**: `"can"` or `"json"`, depending on the switch „Schalten per CAN“ ("switching via CAN").
- **App: login protection** (in operation since 21 Oct, now in the repo): login tokens from `crypto.randomBytes`, comparison in constant time, after 5 failed attempts per IP in 15 min a 15 min lock (HTTP 429), failed attempts and switch commands with IP in the log, optionally a mail to `ALARM_MAIL` from 20 failed attempts per day. ## App – 2026-10-09
- **Progress line stayed permanently:** on 8 Oct, DHW on/off ran through cleanly on the board (switching log: „ok“), but in the app the line stayed on „Bus liest nach“ ("bus re-reads") instead of disappearing after 3 min. - **File format `cmd/regeln` changed:** `{"version":N, "R1":{"an":…,"abstand_min":…}, …, "max_pro_stunde":6, "eigene_regeln_an":false, "eigene":[…]}`. The old field `verdacht` is **rejected with a message** (not reinterpreted – `verdacht: true` meant “R1–R4 on” and would otherwise silently switch on the custom rules). `version` is reported back in the state.
- `cmd/regel`: names `R1`–`R4`, `eigene` (master switch of the custom rules) and custom rules; `verdacht` is rejected with a hint. `regeln/stand` in the new format.
- `substitutions` renamed: `regel_r1_start` … `regel_r4_start`, `regel_abstand_r1` … `_r4`, `regeln_max_h`, `eigene_regeln_start` (up to v22 `verdacht_…`).

## v22 – 2026-09-27
- **Reading on suspicion (experimental), new package `verdacht.yaml`:** the operating modes are read when passive listening suggests a change – exclusively SDO read requests to node 1, never JSON, no periodic polling, only while the bus is alive and outside the start-up pause. **Master switch, default OFF.**
- Fixed rules, individually switchable with minimum interval: **R1** WEM query sequence `2101/0A, 2102/0D, 2102/01` (DHW change), **R2** DHW mode despite known off, **R3** status bits `0x1C1` changed (the previous reason, now switchable, state stored permanently), **R4** heat demand does not match the operating mode (default off). Upper limit for all together per hour (default 6). R1–R4 rest for 2 min after own switch commands.
- **Custom rules** (up to 8): CAN ID + mask + pattern → read heating circuit, DHW or both; stored in flash, switchable by file, via `cmd/regel` and in the web interface („Regel-Befehl“ ("rule command")). `0x601`/`0x581` are blocked as triggers.
- **Configuration by file:** initial values as `substitutions` in the main file; at runtime JSON to `<gerät>/cmd/regeln` (retained), invalid input is rejected with a message; active state retained under `<gerät>/regeln/stand`. Template `regeln.json.example`.
- Web interface: per rule “what and why” and “last triggered”, log of the last ten triggers (rule, read, changed yes/no), also retained under `<gerät>/verdacht/protokoll`.
- **Changed:** with the master switch OFF, a change of the status bits no longer triggers a re-read (up to v21 that always happened). Reading then only takes place at start, after own switch commands and on „Status lesen“ ("read status"). Without the package `verdacht` the old behaviour remains.
